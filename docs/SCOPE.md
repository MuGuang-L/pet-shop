# 必要功能与开发边界

本文件是当前开发范围。历史审查里列出的功能缺口不等于必须全部开发；与本文件冲突时，以此处为准。

目标是一个单店可用的宠物用品商城：买家能找到商品并购买，商家能维护商品、准确履约，订单出问题时可以退款或退货。保持小程序侧与商家网页的操作简单。

2026-10-26 确认：当前全部使用模拟信息。门店名称、地址、电话、营业时间、自提及外送规则继续使用明确标注的演示资料；真实资料不作为本轮模拟版验收的阻塞项。模拟信息不得用于实际配送或对外正式营业。

## 保留并做好

| 范围 | 必要能力 |
| --- | --- |
| 商品 | 分类、搜索、详情、价格、规格、库存、实物图片与适用信息；商家模板建品、上传图片、上下架 |
| 购买 | 购物车、收货地址、费用确认、创建订单、付款、取消；当前保留模拟支付，正式上线再接微信支付 |
| 订单 | 买家查状态；商家看待办、查订单；金额、库存、成交信息保持一致 |
| 履约 | 到店自提与商家外送分开；备货、核销、送出登记；无法履约时有明确处理办法 |
| 售后 | 基础整单退款/退货、审核、验收及退货入库；不为了“功能全”先加复杂售后类型 |
| 门店经营 | 地址、电话、营业时间、接单开关、外送费用与范围说明；基础入库、盘点和库存调整记录 |

首页只承担展示商品、分类及门店必要信息的作用。已有的图片、文案和商品模板保留，目的是方便维护，不扩展成装修平台。

## 不做或暂不做

- 不做吉祥物、品牌故事和装饰性互动。
- 暂不做优惠券、促销活动、会员价、积分、等级、分销、拼团、签到、社交互动。
- 不提前做多门店、复杂员工组织、复杂报表平台。确有日常经营需求时再讨论。
- 部分退款、换货等不自动列为近期任务；先把基础售后做可靠。

## 可靠性属于必要功能

- 查询失败有明确提示和有限重试，避免无限加载及密集重发。
- 写入结果不确定时不能直接当作失败，更不能自动换一个请求重复下单。
- 下单恢复、商品版本检查、事务和必要的幂等保护要保留；重复点击不能重复处理订单。
- 网络异常不清空未提交表单，旧账号的迟到请求不能覆盖新账号状态。
- 数据库连接与事务有等待上限；数据库未就绪时返回明确的不可用状态，不能假装健康或积压写请求。
- 连接恢复后可继续使用；业务数据持久化、可备份、可恢复。
- 主机、数据库和隧道进程的启动、退出和恢复需要可操作的运维办法。进程守护仍需补齐；定时备份代码及恢复演练已完成，运行中的服务更新后还需确认首次自动执行，不用增加新的业务菜单来解决。

低 QPS 使用现有单体 Node 服务和 MongoDB，不引入微服务、消息队列、Redis 或集群作为前置条件。新增代码应对应实际失败场景，并以隔离数据验证，不能破坏共享联调。

正式上线仍需要微信身份与支付接入、正式部署和域名配置、真实商品资料、隐私及售后说明、真机验收。这些是上线条件，不是营销功能。
