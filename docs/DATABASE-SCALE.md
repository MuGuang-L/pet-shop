# 数据增长与事务边界

当前服务使用 MongoDB 副本集，面向低并发的单店经营。服务侧已移除 100 件商品、500 笔历史订单的开发限制。小程序侧的请求、订单状态和返回字段保持兼容。

## 日常请求读取什么

- 下单读取所选商品、当前买家的地址和本次请求的幂等键；重复请求按键读取原订单，历史订单也能核对。
- 订单操作读取目标订单及相关商品。库存调整和退货验收在同一事务中聚合其他未结束订单的预留数量，不把整段订单历史载入内存。
- 商品编辑还检查其他未结束订单引用的规格，不能删除仍在履约的规格。
- 地址只读取当前账号的地址簿。新增库存流水直接追加，不先读取全部旧流水；支付事件也不参与普通请求加载。
- 订单和库存流水列表沿用数据库分页。商品列表仍返回全部商品；旧版 `orders`、`merchantOrders` 保留完整列表语义，仅用于兼容，当前页面使用分页接口。

## 超时与并发

每个普通请求和每次定时任务最多读取 100 笔到期未付款订单并释放预留；指定订单会额外加载，因此即使排在批次之后，已过期订单也不能模拟付款。大量超时积压由后续批次继续处理，定时周期为 10 秒，期间列表状态可能逐批更新。

所有写入继续通过店铺版本号串行提交，并由 MongoDB 重试冲突事务。订单、库存、幂等键、审计在同一事务内提交。局部读取不会把未加载的数据当作删除，也不重排已有记录的位置。商品版本检查和重复请求校验仍然生效。

提货码只与仍可能提货的订单检查重复；已结束订单不会永久占用号码。核销仍同时校验订单和提货码。

日常事务保留 12 秒超时，备份事务为 60 秒。游标使用集合级读取超时，避免当前 MongoDB 驱动在事务的后续批次上错误发送 `maxTimeMS`。写集合不继承该选项，避免 `insertMany` 的二次参数解析冲突。这一配置通过真实跨批次查询和恢复验证；未修改驱动源代码。MongoDB 对普通 `getMore` 的限制见[官方说明](https://www.mongodb.com/docs/v8.0/reference/command/getmore/)。

## 验证证据

`tests/mongo-scale.test.js` 使用独立测试库，包含：

- 2,000 笔历史订单、2,000 条库存流水、2,000 个地址簿与幂等键，以及 123 件原有商品。新增商品、下单、重试、修改商品、采购入库、保存地址和取消订单均成功。
- 七次业务请求合计从数据库返回 3 条订单、6 条商品、1 条幂等键和 2 条流水定位记录，未返回历史全集。索引执行统计确认到期查询不扫描已完成订单。
- 原有订单、地址、流水、幂等键以及无关商品保持一致；被购买后取消的商品只发生预留与释放所需的版本变更，库存恢复原数。
- 207 笔到期订单按 100 条分批关闭，指定的未处理过期单无法支付，重复执行不重复回补。
- 未加载的其他订单继续占用库存容量；退货超容量时整个事务失败，不留下入库记录。
- 完整快照仍包含所有历史；跨多个游标批次备份后，在独立恢复库还原，业务数据完全一致，审计增加一条恢复记录。

完整快照只用于备份、恢复和离线核对。此次结果证明上述数据规模和业务路径，没有将其当作无限容量或高并发承诺。全文搜索、完整商品列表及旧版完整订单列表仍随结果规模增长。保留的 CloudBase 单文档适配器不是当前 MongoDB 部署入口，仍受自身单文档容量限制。

新代码需要 Node 服务重启后生效。启动时补建查询索引，不清库、不重置原有记录。
