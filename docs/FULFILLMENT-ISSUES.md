# 缺货、外送失败与自提延期

商家在订单详情登记履约问题，先与买家确认，再记录处理说明。买家刷新订单可查看原因、约定时间和处理记录。问题单进入「履约问题」待办，不另造一套订单状态。

## 经营流程

| 场景 | 可用处理 | 结束条件 |
| --- | --- | --- |
| 已付款但缺货 | 协商改期、补齐后恢复履约、整单退款 | 继续原备货/发货流程，或完成退款 |
| 已送出但未送达 | 协商改期、登记实际再次送出、整单退款 | 买家确认收货，或完成退款 |
| 已备好的自提订单延期 | 记录约定时间，到店时恢复履约并凭码核销，或退款 | 正确提货码核销，或完成退款 |
| 无法联系买家 | 保留待办、记录后续约定、恢复履约或退款 | 实际履约或退款完成 |

改期不会自动关闭问题，也不会自动取消已付款订单或释放库存。约定时间过后仍保留待办，商家需再次联系买家处理。自提没有默认扣款、没收或到期作废规则。

有未处理问题时，普通发货、备好和自提核销会被拦截，先确认问题已解决。买家实际收到外送商品后仍可确认收货，服务侧会一并结束待处理问题。再次送出保留原配送单号、备注和时间，不覆盖历史。

## 退款与库存

无法履约时可以由商家发起整单退款，金额含原配送费，进入现有售后处理流程；当前仅模拟退款，不产生真实资金流。

发起时逐规格核对：

- 在店或取回数量：实际已核对的商品，不得超过订单数量。
- 可售数量：可以再次销售的商品，不得超过实际核对数量。
- 两者差额记为隔离数量；未在店或未取回部分记为缺失数量。

数量确认后锁定，模拟退款成功时才回补可售数量并记录库存流水；缺货、丢失及隔离部分不加入可售库存。退款失败保留原方案，重试不会重复记账。退款完成不会自动下架商品，剩余可售库存仍需按实物盘点。

买家已先申请仅退款时，商家从原售后单审核，不再另建退款。遇到履约问题的订单必须核对实际数量；不能沿用整单自动释放导致缺货商品重新出现。已有的正常退货验收流程保持独立。

## 接口与重试

商家 `identity.capabilities` 增加 `fulfillment-issues-v1`，Web 仅在服务支持时显示处理入口。

- `recordFulfillmentIssue`：`id`、`type`、`note`、`requestKey`。类型为 `OUT_OF_STOCK`、`DELIVERY_FAILED`、`PICKUP_DELAY`、`CONTACT_UNREACHABLE`；服务端检查订单阶段和履约方式。
- `resolveFulfillmentIssue`：`id`、`issueId`、`issueRevision`、`resolution`、`note`、`requestKey`。`RESCHEDULE` 需 `nextAt`，约定在未来 30 天内；`RESUME` 用于待履约订单；`REDELIVER` 用于外送中订单，可带新 `number`。
- `merchantRefund`：`id`、`issueId`、`issueRevision`、`note`、`requestKey`、`confirm: true`、`items`；每项包含 `productId`、`skuId`、`receivedQty`、`restockQty`。
- 原 `refundReview` 对有履约问题的仅退款单要求 `items` 和 `confirm: true`。无履约问题的旧请求保留原兼容逻辑；新 Web 的未发货仅退款审核也提供数量核对。
- 新动作均仅商家可用。买家继续通过 `order`、`ordersPage`、`tracking` 和原售后接口读取与处理自己的订单。

问题编号与版本共同防止旧页面覆盖新处理。请求键在账号范围内校验，相同参数重试返回当前订单，不重复登记、发起退款或记账。网页在发送前保存原请求；响应丢失后重开订单可核对原提交。已确认保存、但后续刷新失败时明确提示已保存，不引导重复提交。
